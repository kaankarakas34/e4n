# Self profile and billing persistence — 8 October 2026

This is one P39/P30 web package: schema storage, owned API, self profile editing, billing form integration, and acceptance. It does not complete membership entitlements, company eligibility, pricing, shuffle or production release.

## API and data

- `GET /api/user/profile-settings` returns the authenticated database account's settings; another owner cannot be selected by path/body/query. Missing/deleted account is 401. Private/no-store, repeatable-read read-only transaction.
- `PUT /api/users/me` has one active provider, `src/self-profile.js`. Existing profile and billing callers use this route. It selects and locks the current account, writes only supplied fields, captures the minimal saved projection inside the transaction, commits, then returns it. No `SELECT *`, password/reset tokens, permission/status/payment fields or read after commit.
- Fields: name100, profession100, phone20, city100, website2048, bio5000, linkedin_profile255, company255, tax_number50, tax_office100, billing_address5000. Supplied strings are trimmed. Empty optional fields become null; profession is the existing NOT NULL column and clears to an empty string. Name cannot be empty. URL fields require HTTP(S), a host and no embedded credentials. Unknown/protected fields and invalid types/lengths are 400; database errors are redacted and roll back. Field limits match existing varchar columns or explicit new API limits; these are not company proof or tax identity rules.
- `profileSettingsVersion:1`, canonical `id/ownerId`, all profile fields and a SHA256 `revision` form the response. Revision is calculated over editable stored values; no extra revision column or API-time DDL.
- Self editor supplies `expectedRevision`. Changed stale content returns 409. Identical normalized content with an old revision is a replay/readback and does not execute UPDATE. Row locking serializes writes. Existing partial billing/private legacy callers without a revision retain partial last-write behavior; this is not optimistic concurrency protection for every legacy writer.
- Additive migration `server/supabase/migrations/20261008145443_self_profile_fields.sql`, created with pinned Supabase CLI `migration new`, adds only nullable `users.website` and `users.bio`; version ledger entry `0023_self_profile_fields`. Existing migration checksums are unchanged. Fresh source23, app tables46 plus ledger =47. No new table/grant/RLS policy is introduced. Broad existing users RLS/legacy auth paths remain Sprint6 work.

## Web

- Self profile loads current private settings alongside the existing validated public/self view. Read errors show retry and no stale editable profile. Typed transport checks session owner before sending and validates version/owner/fields/revision and saved request values afterward. Full legacy read DTOs are filtered to supported editable fields before PUT; email/role/id/metrics are not editable through this method. Private legacy member screen does not offer self email editing.
- Actual saved name/phone/city/profession/company update the current auth store; other persisted user/session fields are retained. Profile shows canonical stored values immediately and after reload. Website opens an HTTP(S) link; bio stays React-escaped text. City and LinkedIn inputs join existing edit fields. Labels, dialog name, synchronous write lock and disabled controls cover the touched form.
- A failed/lost acknowledgement triggers read-only reconciliation. Matching saved content confirms success without an automatic second PUT; otherwise the draft stays and the user sees an error. A 409 explicitly asks for refresh before another edit. Account/token/route generation guards discard stale responses.
- Billing now awaits the owned, validated saved projection before opening card step and updating the local store. Unknown acknowledgement is reconciled by reading the four billing fields. A failed/nonmatching save keeps step1; no card/payment request is made by this operation. Synchronous submission lock and modal/context generation prevent old replies advancing a different flow. Payment attempt identity/recovery was preserved. Visitor registration keeps its existing separate billing path.
- Removed the unsupported web claim that company fields become management-only permanently after a first save. Existing server capability to edit these text fields is retained. D10 scope/proof/transition/locking remains open; saving a company name does not verify company eligibility.

## Acceptance and release boundary

Focused `self-profile-contract.mjs` passes on actual Express/JWT/PostgreSQL17 and transpiled production TS: fresh23/repeat0/22upgrade, owner-only DTO, protected fields, URL/type/length checks, clearing/partial preservation, eight concurrent edits (one success/seven409), safe replay without UPDATE, trigger failure rollback/redaction, contact visibility, billing compatibility, pre-send stale owner rejection, invalid acknowledgements.

All existing contract bootstrap/upgrade expectations now include the new migration tail. Synthetic restore seeds nonempty Unicode bio and website and checks restored HTTP settings against the restored database, along with unchanged manifest/hash checks.

Full same-source rehearsal and browser evidence are recorded in the delivery note after completion; a passing old report is not reused. The first trial has 34/36 API suites passing and two outdated migration-count assertions failing (smoke visitor upgrade and payment upgrade); it did not reach browser/release acceptance. Both count assertions were corrected and fresh smoke/payment/profile/types checks passed.

No live Supabase write/migration, deployment, real payment or real mail. The new migration must be reviewed/applied in the target environment through the existing live-schema adoption gate before this feature can be accepted there. Code rollback can retain additive columns; dropping columns would destroy profile data and is not a production rollback instruction. Full users/auth/API/Supabase security, D01–D10 decisions, mobile Sprint7 and LMS Sprint8 remain separately open.
