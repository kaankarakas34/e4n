# Isolated E4N API smoke environment

Web activity recording is covered by `node test/activity-record-form.mjs` (actual form/page/summary with controlled hooks and transport), `node test/meeting-read-api.mjs` (actual client ACK/field validation), and `node server/test/meeting-contract.mjs <mobile-root>` (actual web client write and owner-scoped calendar against disposable Express/PostgreSQL). The form preserves existing group/lonca partner scope; unsupported duration/location fields are removed. A confirmed write triggers calendar/summary reads; read failure/retry does not repeat the write. `/calendar` rejects a different owner query (403), anonymous requests (401), and supports only the authenticated owner.

Current schema acceptance: ten migrations and 37 application tables. Migration 0010 creates the score history table already used by the calculator; no historical backfill or score formula change. `node server/test/meeting-contract.mjs <mobile-source-root>` from the repository root tests keyed completed activity writes, one history on replay, activity/score/history rollback on injected failure, requester concurrency and real mobile transport/service. The shared mobile screen test is `node test/mobile-meetings.mjs <mobile-source-root>`. Web completed reads exclude scheduling requests; web create-modal implementation and native device/release integration are separate remaining tasks.

From `server/`, run `npm ci` and `npm run test:isolated`. Docker must be running and the official `postgres:17` image must be available (`docker pull postgres:17` once). The script creates a uniquely named, temporary PostgreSQL 17 container bound to a random **127.0.0.1** port. It applies three ordered schema versions from a blank database: the schema portion of `init.sql` without demo seeds, the current runtime extensions, and the three tables formerly defined only in separate scripts. It inserts only synthetic `example.invalid` fixtures, then probes the local API. The container is stopped and removed in a `finally` block.

The script clears production database URL variables and prevents `.env` loading before it imports application code. It never copies live Supabase rows, invokes payment, sends email, or changes the existing Docker Compose database. The report verifies public and admin event listings against future, past and draft fixtures. It also checks that reading the list leaves stored event statuses intact and records constraint failures for `group_members`, `power_team_members`, and `visitors` using rolled-back transactions.

`init.sql` creates `groups` without `meeting_day`; `runMigrations()` now adds it before altering its type. The harness checks clean setup to 34 application tables, safe reapplication with no new versions, checksum mismatch rejection, refusal to adopt an existing unversioned database automatically, and that an induced missing-table error reaches the caller. It no longer uses a local schema shim.

The chain now includes `0005_public_visitor_inviter`. The harness also rehearses an existing 0001–0004 database with a preserved visitor row, and calls visitor application/status and ticket-list endpoints after removing request/import-time DDL. The manual HTTP migration endpoint must return 404. The non-Vercel startup path uses the versioned runner and refuses an unreviewed unversioned database; Vercel does not apply migrations on import. Production's existing unversioned Supabase schema still requires a separate backup, adoption rehearsal, and deployment order before these API changes are released.

`npm run migrate` now invokes the versioned runner and the harness checks it applies 0 versions on an up-to-date isolated database. The old `migrate_supabase.js` init/seed helper is disabled unless explicitly opted in with `E4N_ALLOW_LEGACY_SEED=1`; it is not a production upgrade path. Scheduled jobs are disabled when `NODE_ENV=test` so the event fixture cannot change during an HTTP smoke run.

The versioned runner is currently **rehearsal only**. It does not run automatically on app startup or against Supabase. Version `0002` freezes the legacy runtime schema code in `migrations/0002_runtime_extensions.js`; the old import path is a compatibility wrapper. A reviewed adoption path for existing schemas, live column/constraint drift, request-time DDL removal, and rollback plan are required before production use. Do not treat the 34-table name count as proof that source columns match live Supabase.

This is a repeatable **source-schema** test environment, not a clone of the live Supabase schema. The live `notifications` columns, other schema drift, Supabase Auth/Storage and production scheduling still need separate isolated verification before related changes are considered complete.

## Focused meeting request acceptance

Run `node test/meeting-contract.mjs` from server (or `node server/test/meeting-contract.mjs` from root). Uses disposable loopback-only PostgreSQL 17 and synthetic users; all DB environment values are overridden before imports. The seven-version schema includes `0007_meeting_requests`: a separate request table and a nullable legacy activity update timestamp. The test rehearses upgrading an existing six-version database while preserving its activity rows and scores. Real Express and the real client verify creation, same-key retry without duplicate records, payload conflicts, incoming/outgoing ownership, anonymous rejection, recipient-only decisions, repeat decisions, and an opposing decision race with one winner. An induced GET failure must reject in the client. No production database, email or payment calls; the container is removed on exit.

From root, `node test/meeting-flow.mjs` exercises the actual shared hook, both meeting views and the request modal through a controlled React hook harness. It covers read/error/retry presentation, truthful status labels, write acknowledgement versus refresh failure, duplicate-click protection, session/unmount boundaries, stable request keys on uncertain retries and date validation. This is component logic verification, not a browser or mobile acceptance test. Clean setup now has 35 application tables and seven schema versions; table counts do not prove compatibility with live Supabase. Review backup/adoption and deployment order separately before production release.

## Payment ownership and reconciliation flow

From root run `node server/test/payment-flow.mjs`. It creates a disposable PostgreSQL 17 container and a **local synthetic Sipay HTTP server**, then runs the real Express initiation/status/callback paths and real client API. No real provider or SMTP is contacted. Tests cover authenticated ownership, guest invoice receipt boundaries, status-request hash field order, matching invoice/amount/settled Auth results, pending/preauthorization rejection, concurrent/repeated/late callbacks, rollback and retry without a second initiation, membership changes, event attendance/ticket uniqueness and visitor NULL-event duplication. Legacy unowned member payments remain unassigned and cannot activate an account from action_data alone. Provider settings are set to the local server before app import. The general isolated harness explicitly removes all Sipay settings and now verifies that unverified callbacks leave state intact.

`node test/payment-modal-lifecycle.mjs` and `node test/payment-api.mjs` check the actual TSX/client through controlled hooks/fetch: popup messages require the active invoice, server confirmation precedes consumer success, unresolved attempts have a status-only recovery action, session/action changes discard stale results, and malformed responses are rejected. Browser/Expo and real provider sandbox integration are separate release gates.

This package does not choose D07 pricing/renewal policy or assign old NULL-owned transactions. Existing client price/promo selection and event payment-to-PRESENT behavior are retained pending their policy tasks; this is not complete payment entitlement/security acceptance. Sipay URL/app ID/secret/merchant key must now be explicitly configured; embedded fallback credentials are no longer used. Status reconciliation uses the documented [Check Status](https://apidocs.sipay.com.tr/check-status-25727396e0) contract. Event email notification starts after commit and is not a durable outbox delivery guarantee. Guest receipt lifetime is 24 hours and the web keeps it only in the current modal session.
