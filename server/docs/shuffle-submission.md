# P29 / P31 / P39 — recoverable shuffle submissions

The current web shuffle now sends `requestId`, `expectedRevision`, and the complete frozen `assignments`. Lowercase UUIDs, a mandatory SHA256 source revision, exact top-level keys, unique members and bounded valid assignment arrays are required for keyed commands. Existing legacy callers without a request ID remain compatible and do not acquire an idempotency guarantee.

The request UUID is the immutable `shuffle_execution_history.id`. An optional versioned submission fingerprint in the existing `after_snapshot` binds the expected source revision and every target group (including empty groups) and member. Group and member order are normalized for hashing. No new table, migration, period schedule, scoring rule or payment eligibility is introduced. Schema stays at24 migrations/47 tables. Migration0019 and current baseline migrations must already be installed.

Under the existing group mutation advisory lock and transaction, current DB ADMIN authorization is checked before replay lookup. A same-owner same-ID same-command replay returns the original minimal receipt before inspecting the current source revision: later group/user changes cannot cause the old intent to execute again. A different payload, another owner's ID, or a legacy execution ID returns409. First execution, role reset, archive/upserts, capacity assertion and history receipt all commit together; a history failure rolls all mutations back. A successful receipt contains version/success, current owner, request/execution ID, source/result revisions and the complete-command fingerprint; it is not a statement that those placements are still current.

GET `/api/admin/shuffle-submissions/:id` returns only the initiating current administrator's minimal receipt (private/no-store, no query override; invalid400, absent/foreign/legacy404, deleted401, revoked403). It never changes placements/history. The browser transport validates owner, both IDs, source revision, valid result revision and computed full-command fingerprint before accepting either POST or GET success.

The web stores a frozen command in owner-scoped tab session storage before writing. A synchronous lock stops double-click replacement. Unknown POST outcome triggers only GET reconciliation; failed reads retain the full pending intent and disable new previews. Reload restores the same command. The user may check the receipt or explicitly retry the same command/UUID. Definite400/409/422 plus an absent receipt clears the rejected draft; transient/unknown outcomes do not. A verified receipt clears pending before refreshing current workspace, so a failed list refresh cannot recreate the shuffle. Corrupt/unavailable session state blocks new writes and directs the operator to execution history. Account/role/token changes and unmount generations prevent stale acknowledgements from changing another account's state. This mechanism survives reload in the same tab, not cleared browser storage or a new device.

Current existing global leadership reset, raw profession matching and assignment semantics are preserved. Canonical four-month period, fee/grace/cutoff, service classification, admission, final leadership and reliable notification rules remain open. No notification/email or payment is sent. Legacy API callers that omit request IDs are still not safe for blind retry. Old execution rows are not backfilled or relabelled as keyed receipts. P29/P31/P39/P37 remain In Progress and releaseReady=false; mobile7/LMS8 are excluded.
