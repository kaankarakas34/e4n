# Durable group membership row history

Migration0020 (Supabase CLI-created 20261007181257_group_membership_history.sql) observes every current group_members row as BASELINE, then records INSERT/meaningful UPDATE/DELETE in the same transaction through an invoker trigger. Failed history insertion aborts the membership statement. An identical update produces no duplicate. The table has no subject/group FK so deletion cannot cascade away the history. Names and the relevant before/after group, role, status and joined_at are stored as observations; a parent already deleted during cascade can have an unknown name. Earlier entries retain their captured names.

Changing the row's user_id records separate entries for the previous and next subject with only each subject's relevant side; one member cannot receive another member's state. Changing group_id preserves both sides for the same subject. Source truncate is blocked because it skips row history. History UPDATE/DELETE/TRUNCATE are blocked by triggers. These are application integrity controls, not protection against a privileged owner disabling triggers. RLS is enabled; PUBLIC/anon/authenticated table and helper-function permissions are revoked. Functions are invoker with qualified relations and a fixed search path. The API database role must be authorized to write this private history through the trigger before any production adoption.

GET /api/membership-history reads only the current actor's subject history; GET /api/admin/membership-history/:id requires current DB ADMIN and permits preserved history of deleted subjects. Actor UUID/current-role/query/cursor validation and private no-store responses guard access. Every page uses read-only repeatable-read with a15s statement timeout, full subject count and at most50 entries. Cursor pair preserves six microsecond digits and UUID tie ordering; SQL uses the user/time/id index. Separate pages are separate snapshots, not a claim of a globally frozen history under concurrent commits.

Web /membership-history and /admin/membership-history/:id show previous/next records, real counts, refresh and older-page loading with account/role/token/target isolation. Links are in group management and membership record detail. Loading, empty, failures and forbidden admin access are distinct. Raw membership-row role is identified as the role stored on the connection; it is not a newly computed effective account role.

Migration0025 (CLI-created 20261009073843_membership_operation_context.sql) adds nullable operation_context: actorId, captured actorName, technical action and operationId. Mounted closed-group application/status/removal/transfer/role/shuffle and group/account deletion writers set transaction-local context after current database authorization. The actor is taken from the authenticated identity and its current database name; request bodies cannot supply it. All row changes in one operation share the same UUID. Commit/rollback clears context on pooled connections. Actor renaming/deletion does not rewrite captured names. Both public and admin shuffle writers are covered. Unmounted legacy users routes are outside this coverage. Lonca/power-team histories are separate from this closed-group ledger.

Existing rows and direct database changes without context remain null; no earlier actor is inferred. Owner/admin APIs expose the added field and the web screen shows the actor, action and expandable operation identity. Invalid provenance is rejected by the web DTO. The trusted API database connection can set this local context; a privileged database owner can forge it or disable triggers, so this is application provenance, not a tamper-proof independent audit.

This is technical connection history. A technical action does not assign a policy removal cause, score threshold, eligibility, final approval authority, canonical period or one-active-group rule. There is no backfill of deleted data, no auto-prune/retention policy and no live schema adoption. Application rollback must preserve the ledger and triggers; destructive downgrade is only a disposable test technique. Production schema rollback/restore requires its own reviewed backup and P09/P36 plan.
